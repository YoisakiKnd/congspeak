# 0.3.2 语音稳定性修复记录

2026-11-17，用户反馈：Windows 语音激活通话在一次疑似丢包后，对方持续听不到自己，但原始麦克风电平仍在变化。**尚未在 Windows 真机复现这一具体故障，不能把下面任何一项直接认定为该反馈的根因。**

## 已修复的恢复缺口

- 原先 DSP 错误只会留下错误并把帧清零，不会重建处理图。现在对错误、panic 和非有限输出隔离，短暂退避 100 ms 后重建，再继续处理；不会自动关闭降噪/AEC 或绕过用户设置。
- 原先采集积压超过 100 ms 会清空整批声音；大回调或调度较慢时可能反复饿死语音激活。现在保留最新 40 ms，丢弃旧语音片段。
- 原先只看流对象是否存在，无法识别对象仍在但回调已经停止。现在监视真实回调计数，持续 2 秒无进展视为停滞，进入设备重建；零电平但仍有回调的正常静音不会触发。
- 输入/输出流恢复或默认设备变化后，同步清除旧 PCM、重采样状态和 DSP 状态，不保留失效 AEC 参考。保留麦克风静音、发言模式、设备选择和连接。
- 接收侧迟到、重复、损坏包只计入丢弃数，不再永久挂成“麦克风处理错误”。接收解码的异常被限制在播放队列中，不会继续向外展开导致采集线程退出。
- 去掉音频线程私自执行、与会话状态不同步的 120 秒 PTT 截止；松开键仍会停止发送。该项与用户已确认的“语音激活”反馈无关。

接收解码的确定性复现：上游 `AudioQueue::get_next_data` 在一次部分读取后，遇到样本数更短的损坏包，解码失败留下旧 `decoded_pos`，后续读取对长度 240 的缓冲执行 `drain(..960)` 并 panic。测试先证实旧路径会 panic，再验证新的接收边界重建播放队列并接受后续正常语音。普通 UDP 丢包并不等价于这种损坏包；不能据此声称已复现用户的 Windows 故障。

## 诊断与恢复入口

音频设置新增：已编码/提交发送/本机发送队列丢弃/接收丢弃计数，以及 DSP、设备和接收解码恢复次数。语音激活时原始声音达门限但处理后不触发，会显示专门原因。

“重启音频（保留连接）”会重建流与处理图，不需退出客户端。诊断按钮生成最近约 120 秒、每秒一次的内存状态，包含处理设置和音频计数，不含录音、服务器凭据、身份密钥或聊天内容。系统拒绝剪贴板访问时，可在展开的只读文本框中全选复制；不自动上传诊断。

## 验证结果

- 14 项核心/音频测试通过。新增覆盖：DSP 非有限输入后重建并重新触发语音激活；持续接收丢包下 VAD 继续工作；丢包、重复、乱序、序号回绕后接收继续；损坏包队列恢复；回调看门狗；采集积压保留最新声音。
- 桌面、协议、音频及全部 example 的严格 Clippy `-D warnings` 通过；TypeScript/Vite 构建通过。
- macOS 实际设备短时测试：接收故障后继续编码 231 帧；显式重启后继续编码 92 帧。输入增益为零，输出只播放合成测试音，不联网。
- 授权服务器静音互通：实际 CPAL → 零增益 DSP → Opus → Session → TS3 → 第二临时客户端收到 41/41 包；PTT 空闲/释放和静音关闭采集通过。未传输环境声音。
- 原生界面确认诊断计数、音频重启提示和可复制的只读诊断文本入口。检查期间未连接服务器、麦克风保持静音。
- Windows x64 单文件完成交叉构建及 PE/DLL 导入检查；未在 Windows 硬件执行新版本。

持续设备测试（标称至少 150 秒）：故意触发接收解码异常，并持续注入丢包/重复/突发包与短暂发送条件丢失，之后继续编码 8,604 帧；显式重启后继续编码 91 帧。输入增益为零，不联网。测试日志中的 panic hook 是已捕获的故障注入，进程最终正常 PASS。详细记录见同目录 AUDIO.md 的 0.3.2 节。

## 仍然存在的边界

这不是“稳定版认证”。尚缺 Windows 上该故障的复现、较长时间的官方客户端双向人声通话、设备插拔/蓝牙切换及真实弱网重连测试。自动恢复不能绕过服务器授予的发言权、离开状态或用户静音；声学处理未出错但抑制不合理的情况，也不能仅凭能量值安全判定并自动关闭 AEC。

## 0.5.7 原生版回归

- 短暂断线后更新连接代数，清除旧用户编号对应的播放和音量状态。新连接同步完成后恢复订阅。同步或重连期间拒绝聊天和管理操作，未确认的请求提示结果未知。
- 私聊按用户 UID 校验，输入草稿随标签页保存。需要确认目标身份的用户操作在执行前核对 UID。桌面端直接等待服务器确认结果。
- 全局发言键独立更新按键状态，释放后的旧语音帧会被拦截。切换音量时可继续使用当前音频流。接收队列溢出计入诊断。
- 本地配置通过临时文件写入并原子替换。读取损坏配置时显示错误，正常退出会等待待保存的偏好设置。
- 授权测试频道通过 UDP 中断回归。客户端重新连接，拒绝旧代数的请求，新代数的订阅收到服务器确认。独立零增益测试中，对端解码了 40 个语音包，松开 PTT 后停止发包，静音后采集关闭。
- macOS 实际音频设备运行 30 秒接收故障回归，包含损坏、丢失、重复和突发语音包。捕获解码异常后继续编码 1,734 帧，手动重启后继续编码 91 帧。该回归采用持续发送模式和零增益。
- 工作区 21 项测试通过，Clippy 通过。Windows 单文件完成交叉编译及校验。Windows 真机语音激活、设备切换和长时间双向通话仍待验收。

## 0.5.8 接收队列溢出恢复

旧版将协议层的 `Maximum length exceeded for command queue` 和 `Maximum length exceeded for fragment queue` 作为连接终止错误。新版释放已失效的会话，用原身份重连并核对服务器公钥。如果服务器报告原会话仍在线，每隔 4 秒重试，恢复流程最多等待 45 秒。一分钟内重复溢出时会显示错误，避免持续重连。

在授权服务器连接中注入了与命令队列溢出相同的错误类型。恢复后回到原频道，身份一致，订阅命令收到确认。macOS 使用零增益持续发送，故障前后均提交了语音包，中间没有切换麦克风设置。另有自动测试覆盖两种队列错误的分类。Windows 真机上的原始错误全文和语音激活场景仍待核实。
